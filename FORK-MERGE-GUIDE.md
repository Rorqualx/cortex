# Fork Merge Guard — Protecting Config Integrity on Upstream Merges

This system prevents the silent config breakage that happens when upstream merges
overwrite fork-specific changes without triggering conflicts.

## The Problem

Git's merge algorithm resolves changes at the line level. If upstream modifies a
config file that the fork also modified, but on _different lines_, Git merges
cleanly — even if the combined result is semantically broken. The `merge=ours`
strategy in `.gitattributes` handles _conflicting_ edits, but can't protect
against changes upstream makes to lines the fork doesn't touch.

## The Defense

Three layers:

### Layer 1: Config Baseline Snapshots (`fork-config-baseline.json`)

A JSON snapshot of critical config file hashes and structural properties (top-level
keys, merge=ours entries, package sections). Generated by the fork team and
committed to the repo.

- **Generate:** `node scripts/fork-config-snapshot.mjs generate`
- **Verify:** `node scripts/fork-config-snapshot.mjs verify`
- **Diff:** `node scripts/fork-config-snapshot.mjs diff`

### Layer 2: Pre-Merge Dry-Run (`scripts/fork-merge-guard.mjs`)

Runs before committing an upstream merge. Does a `--no-commit` merge and checks:

1. Working tree is clean
2. Baseline is current
3. Merge applies cleanly
4. No conflict markers remain
5. Protected files weren't modified
6. Fork-exclusive paths exist
7. `.gitattributes` merge=ours count unchanged
8. TypeScript compiles (optional)
9. Post-merge drift report

**Usage:**

```bash
# Dry-run only (safe — doesn't commit)
node scripts/fork-merge-guard.mjs upstream/main

# Auto-commit if all checks pass
node scripts/fork-merge-guard.mjs upstream/main --apply

# Skip TypeScript check for speed
node scripts/fork-merge-guard.mjs upstream/main --skip-tsc
```

### Layer 3: Post-Merge Verification (`scripts/fork-merge-verify.mjs`)

Run after the merge is committed to confirm nothing broke:

```bash
# Full check
node scripts/fork-merge-verify.mjs

# Quick check (skips TSC and tests)
node scripts/fork-merge-verify.mjs --quick

# Regenerate baseline after passing
node scripts/fork-merge-verify.mjs --regenerate
```

### Layer 4: Pre-Commit Hook

A local pre-commit hook runs config drift detection when critical files change.
If `fork-config-baseline.json` drifts from the current state, the commit is
blocked until you either fix the issue or regenerate the baseline.

## Merge Procedure

### Standard Upstream Merge

```bash
# 1. Fetch latest upstream
git fetch upstream

# 2. Ensure you're on the fork branch
git checkout memory-fork

# 3. Run the merge guard (dry-run)
node scripts/fork-merge-guard.mjs upstream/main

# 4. If all checks pass, apply
node scripts/fork-merge-guard.mjs upstream/main --apply

# 5. Run full verification
node scripts/fork-merge-verify.mjs

# 6. If verification passes, update baseline
node scripts/fork-merge-verify.mjs --regenerate

# 7. Push
git push origin memory-fork
```

### If Problems Are Found

1. **Conflict markers:** The merge guard aborts automatically. Resolve manually.
2. **Protected files touched:** Review the changes. If upstream modified a file
   that's `merge=ours`, check whether `merge=ours` is working (it should have
   kept your version). If upstream added new code to a section your fork doesn't
   touch, you may need to manually integrate.
3. **Fork paths missing:** Upstream didn't delete them (they're fork-exclusive),
   so this shouldn't happen. If it does, check for accidental directory renames.
4. **TypeScript errors:** Likely a breaking API change. Fix, then re-verify.
5. **Config drift:** Expected after upstream changes. Verify the changes are
   benign, then regenerate.

### Adding New Protected Files

1. Add the path to `.gitattributes` with `merge=ours`
2. Add the path to `PROTECTED_FILES` in `scripts/fork-merge-guard.mjs`
3. Add to `FORK_EXCLUSIVE_PATHS` in `scripts/fork-config-snapshot.mjs` if fork-exclusive
4. Regenerate baseline: `node scripts/fork-config-snapshot.mjs generate`

## Why Not Just Use merge=ours Everywhere?

`merge=ours` only works when there's an actual conflict. If upstream changes
a different part of the same file, Git merges both changes — and the combined
result may be invalid. The baseline system catches these silent combinations.

## Cron Job Disaster Recovery

Cron jobs are stored at `~/.openclaw/cron/jobs.json` (and `.bak` backup). If the gateway loses jobs from memory (e.g., after API credit exhaustion causes cascading errors):

1. Read `~/.openclaw/cron/jobs.json` or `.bak` — the disk files persist
2. Recreate each missing job via `cron add` with the original payload
3. The backup file (`jobs.json.bak`) is the authoritative safety net

## When to Regenerate the Baseline

- After a successful upstream merge
- After adding/removing protected files
- After intentional changes to tracked config files
- Never mid-merge (regenerate after resolving)
